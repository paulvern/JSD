Guida a JSD Emulator Hub

Questi emulatori non sono pensati soltanto per “far partire un gioco”. Il progetto è soprattutto un laboratorio di emulazione, reverse engineering e recupero di risorse: quando l’hardware e il formato lo permettono, l’obiettivo è osservare il funzionamento della macchina, disassemblare o ricostruire il codice, estrarre grafica e registrare o ricostruire i suoni.

Ogni core resta in un file HTML separato. La landing riconosce il sistema, può guardare dentro agli ZIP e passa ROM e BIOS soltanto quando il BIOS è realmente necessario e riconoscibile. I file rimangono nel browser.

JSD Emulator Hub Guide

These emulators are not intended only to “run a game”. The project is primarily an emulation, reverse-engineering and asset-recovery laboratory: when the hardware and file format allow it, the goal is to inspect the machine, disassemble or reconstruct code, extract graphics, and capture or reconstruct sound.

Each core remains in a separate HTML file. The launcher detects the system, can inspect ZIP archives, and passes ROMs and BIOS files only when a BIOS is genuinely required and positively identified. Files remain inside the browser.

01 · Cosa significa “decompilare” una ROM

Una ROM commerciale contiene codice macchina e dati, non il progetto originale. Per questo gli strumenti del progetto lavorano a più livelli:

  • Disassembler: traduce le istruzioni macchina in assembly leggibile (Z80, LR35902, ARM/Thumb, 6809, CP1610 a seconda del sistema).
  • Analisi/decompilazione euristica: prova a distinguere codice raggiungibile e dati, segue salti e chiamate, individua punti d’ingresso e crea etichette artificiali.
  • Memoria e trace: permette di osservare RAM/ROM/VRAM, registri CPU e istruzioni eseguite durante il gioco.
  • Grafica: estrae tile, sprite, OAM, palette, VRAM, fotogrammi o segmenti vettoriali. Il tipo di risorsa dipende dalla macchina.
  • Suono: quando possibile registra scritture ai chip audio, registri per fotogramma e/o genera un WAV dalla sequenza emulata.
Limite fondamentale: il sorgente originale non può essere ricostruito fedelmente. Nomi delle variabili, commenti, macro, file sorgente, strumenti grafici e struttura originale del progetto non sono conservati nella ROM. Il risultato è una ricostruzione tecnica utile per capire il programma, non il codice sorgente originale.

Grafica e suono: cosa viene davvero estratto

Quando una console usa sprite e tile hardware possiamo esportare strutture vicine agli asset del gioco. Quando invece la grafica è una bitmap, come sullo Spectrum, possiamo catturare lo schermo o ritagliarlo ma non esiste uno “sprite hardware” da estrarre. Sul Vectrex la grafica è vettoriale: quindi si esportano segmenti e fotogrammi SVG/JSON. Per l’audio, un WAV ricostruito rappresenta ciò che il modello del chip sta producendo; non implica che nella ROM esistesse un file WAV originale.

01 · What “decompiling” a ROM means

A commercial ROM contains machine code and data, not the original project. The tools therefore work at several levels:

  • Disassembler: converts machine instructions to readable assembly (Z80, LR35902, ARM/Thumb, 6809, CP1610 depending on the system).
  • Heuristic analysis/decompilation: tries to separate reachable code from data, follows jumps and calls, identifies entry points and creates synthetic labels.
  • Memory and trace: exposes RAM/ROM/VRAM, CPU registers and executed instructions while the game runs.
  • Graphics: extracts tiles, sprites, OAM, palettes, VRAM, frames or vector segments depending on the machine.
  • Sound: where available, records sound-chip writes, per-frame registers and/or renders WAV audio from the emulated sequence.
Fundamental limitation: the original source cannot be faithfully recovered. Variable names, comments, macros, source files, art tools and the original project structure are not preserved in the ROM. The output is a technical reconstruction useful for understanding the program, not the original source code.

What graphics and sound extraction actually produce

On machines with hardware sprites and tiles, exports can be close to the game’s underlying assets. On a bitmap machine such as the Spectrum there is no hardware sprite to extract, so the tool captures or crops the screen instead. Vectrex graphics are vectors, so the natural export is SVG/JSON vector data. A reconstructed WAV represents the sound generated by the emulated chip; it does not imply that the original ROM contained a WAV file.

02 · Landing, ZIP e BIOS

La landing può analizzare una cartella intera e le entry interne degli archivi ZIP. Usa estensioni, dimensioni e firme note — per esempio logo Nintendo, header GBA, TMR SEGA, header Coleco, header MSX — per scegliere il core corretto.

  • ZIP: le ROM interessanti vengono estratte in memoria quando il browser supporta il metodo di compressione. ZIP cifrati, ZIP64 o metodi non supportati possono essere riconosciuti ma non estratti.
  • BIOS: non viene scelto soltanto perché è un .bin o .rom. Deve corrispondere a sistema, dimensione attesa e nome/firma coerente.
  • Sega e Game Boy: il launcher non carica automaticamente un BIOS perché non è necessario per l’uso normale della versione inclusa.
  • Fullscreen: puoi usare quello interno del singolo emulatore oppure il pulsante fullscreen della barra della landing. Esc esce dalla modalità a schermo intero.

02 · Launcher, ZIP archives and BIOS handling

The launcher can inspect a whole folder and the entries inside ZIP archives. It uses extensions, sizes and known signatures — for example the Nintendo logo, GBA header, TMR SEGA, Coleco headers and MSX headers — to choose the appropriate core.

  • ZIP: interesting ROM entries are extracted in memory when the browser supports the compression method. Encrypted ZIPs, ZIP64 and unsupported methods may be detected but cannot necessarily be extracted.
  • BIOS: a file is not selected merely because it is a .bin or .rom. It must match the system, expected size and a coherent name/signature.
  • Sega and Game Boy: the launcher does not automatically load a BIOS because the included builds do not require one for normal use.
  • Fullscreen: use either the emulator’s own fullscreen button or the launcher player fullscreen. Press Esc to leave fullscreen.

Game Boy · Game Boy Color · Game Boy Advance

GBxJSD · GBC · JSD ARM7TDMI clean core

File e avvio

ROM .gb, .gbc, .gba e, quando appropriato, .bin. Nessun BIOS esterno è richiesto dalla landing. GB/GBC usano il core interno; GBA usa il nuovo core JSD ARM7TDMI indipendente, caricato localmente solo quando serve.

Comandi

  • Frecce o WASD: D-pad
  • Z: A · X: B
  • Invio: Start · Shift: Select
  • GBA: Q: L · E: R

Reverse engineering

Dump della memoria con mappa CPU e ROM fisica; disassembler LR35902 bank-aware per GB/GBC; disassembler ARM7TDMI ARM/Thumb per GBA con branch, load/store, ALU, stack e SWI. Esportazione ASM.

Grafica e audio

GB/GBC: tile 2bpp, tilemap e OAM. GBA: tile BG/OBJ 4bpp/8bpp, palette e 128 oggetti OAM. Export PNG/JSON e screenshot. Per GB/GBC il monitor audio espone l’APU a 4 canali e il relativo stato; il nuovo core GBA registra i registri audio e offre un monitor audio di base, ma DirectSound non è ancora completo.

Stato / salvataggi

Export/import dello stato e della RAM dove supportato dalla modalità corrente.

Limitazioni

Il core GBA è una implementazione JSD indipendente in JavaScript con BIOS HLE sperimentale. Implementa una parte ampia di ARM/Thumb, mappa memoria, DMA/timer/IRQ approssimati, modalità video 0–5, BG e OBJ di base e diverse SWI BIOS comuni. Restano incompleti o approssimati timing cycle-perfect, finestre/blending, OBJ affine completo, DirectSound, EEPROM e periferiche cartuccia insolite. Per GB/GBC l’audio modella molti dettagli, ma non tutte le anomalie analogiche. Il disassembly GBA è statico e non ricostruisce il C/C++ originale.

Files and boot

ROMs: .gb, .gbc, .gba and, where appropriate, .bin. The launcher requires no external BIOS. GB/GBC use the internal core; GBA uses the new independent JSD ARM7TDMI core, loaded locally on demand.

Controls

  • Arrows or WASD: D-pad
  • Z: A · X: B
  • Enter: Start · Shift: Select
  • GBA: Q: L · E: R

Reverse engineering

CPU-mapped and physical-ROM memory views; bank-aware LR35902 disassembly for GB/GBC; ARM7TDMI ARM/Thumb disassembly for GBA including branches, load/store, ALU, stack and SWI. ASM export.

Graphics and audio

GB/GBC: 2bpp tiles, tilemaps and OAM. GBA: 4bpp/8bpp BG/OBJ tiles, palettes and 128 OAM objects. PNG/JSON export and screenshots. For GB/GBC the audio monitor exposes the four-channel APU and its state; the new GBA core logs audio registers and provides a basic audio monitor, while DirectSound is not yet complete.

State / save data

State and RAM export/import where supported by the active mode.

Limitations

The GBA core is an independent JSD JavaScript implementation with an experimental HLE BIOS. It implements a broad ARM/Thumb subset, memory mapping, approximate DMA/timers/IRQs, video modes 0–5, basic BG/OBJ rendering and several common BIOS SWIs. Cycle-perfect timing, windows/blending, complete affine OBJ support, DirectSound, EEPROM and unusual cartridge peripherals remain incomplete or approximate. GB/GBC audio models many details but not every analogue quirk. GBA disassembly is static and does not reconstruct the original C/C++ source.

Commercial BIOS and ROM files are not included. WAV export comes from the current audio model and does not reconstruct original music source files.
